# Agent guide

How this project is put together, the rules it follows, and how to extend it
without breaking them. Read this before changing anything; the README covers
day-to-day commands for people.

## Stack

| Layer      | Choice                                                        |
| ---------- | ------------------------------------------------------------- |
| Framework  | Next.js 16 (App Router), React 19                             |
| CMS        | Payload 3, admin at `/admin`, REST at `/api` (GraphQL is off) |
| Database   | Postgres 17 via `@payloadcms/db-postgres`, migrations only    |
| Email      | SMTP via `@payloadcms/email-nodemailer`; Mailpit in dev       |
| Runtime    | Node 24 (`.nvmrc`, Dockerfile, `engines`), pnpm 11            |
| Production | Docker Compose on a VPS: Postgres, migrate job, app, Caddy    |
| Tests      | Vitest (`tests/int`), Playwright (`tests/e2e`), separate DB   |

Payload has a skill with full reference docs: start at
`.claude/skills/payload/SKILL.md`. For Next.js, read the guide in
`node_modules/next/dist/docs/` before using an API; this version differs from
older training data (examples below).

## The rule behind most decisions: dev and production must not drift

Local development behaves like production wherever it can, so a bug seen in one
reproduces in the other and a feature that works locally works when deployed.
Concretely:

- Same Postgres image and major version in dev, CI and production.
- Schema changes only through migrations, everywhere (`push: false`).
- Email always goes over SMTP; dev just points it at Mailpit.
- Security headers come from `next.config.ts`, so dev sends them too.
- Same Node major locally (`.nvmrc`), in CI and in the Docker image.

When you add something, prefer the option that behaves the same in both. If a
difference is unavoidable, say so in a comment where it lives.

```

  app/

  components/
    admin/               admin-panel components (BackupPanel on the dashboard)

  lib/
    backup/              backup create/restore, admin endpoint (see Backups)
    site.ts              site name, language, URL, privacy-policy path, GA ID

  migrations/            generated by `payload migrate:create`; always committed
  env.ts                 server env vars, validated at startup
  payload.config.ts
  payload-types.ts       generated by `pnpm generate:types`; always committed

tests/
  setup/                 test database creation + migration (shared by Vitest/Playwright)
  int/                   *.int.spec.ts run in Node; *.int.spec.tsx run in jsdom
  e2e/                   Playwright, against a server on port 3100
```

## Commands

```bash
pnpm dev                        # app on :3000 (needs `docker compose up -d`)
pnpm check                      # lint + typecheck + prettier; run before committing
pnpm test:int                   # integration and component tests
pnpm test:e2e                   # Playwright; starts its own server on :3100
pnpm payload migrate:create <name>
pnpm payload migrate
pnpm generate:types             # after any collection/field change
pnpm generate:importmap         # after adding/removing custom admin components
pnpm backup:create [dir]        # full backup to ./backups (see README → Backups)
pnpm backup:restore <file.tar>
```

## Recipes

### Change the schema (collections, fields, globals)

1. Edit the collection in `src/collections/` and register it in
   `payload.config.ts`.
2. `pnpm payload migrate:create <short-name>` then `pnpm payload migrate`.
   Never skip this: with `push: false` the local database won't change
   otherwise, and CI fails a schema change that has no migration.
3. `pnpm generate:types` (and `pnpm generate:importmap` if you added admin
   components).
4. Commit the collection, the migration files, `payload-types.ts` and
   `importMap.js` together.

New collections:

- Set `access` explicitly with the helpers in `src/access/`. Payload's default
  lets any logged-in user do anything, so leaving it out is a decision too.
- If the frontend shows the collection's documents, add
  `hooks: revalidateOnChange('<slug>')` (see caching below).

Roles: `users.role` is `admin` or `editor`. Admins manage users; both manage
content unless a collection says otherwise. The first user created is always an
admin. The role is saved in the JWT, so checks don't hit the database.

### Fetch Payload data in a page

Two constraints:

- **Nothing may query the database at build time.** The Docker build has no
  database (see the Dockerfile). A page that queries Payload must render at
  request time, so call `await connection()` (from `next/server`) before the
  query. The same goes for `sitemap.ts`, `robots.ts` and `generateMetadata`.
  Don't use `generateStaticParams` with Payload queries.
- **Cache the query, not the page.** Wrap Local API calls in `unstable_cache`
  with the collection's tag; the collection's `revalidateOnChange` hook clears
  it when an editor saves.

```tsx
import config from '@payload-config'
import { unstable_cache } from 'next/cache'
import { notFound } from 'next/navigation'
import { connection } from 'next/server'
import { getPayload } from 'payload'

import { cacheTag } from '@/lib/revalidate'

const getPage = unstable_cache(
  async (slug: string) => {
    const payload = await getPayload({ config })
    const { docs } = await payload.find({
      collection: 'pages',
      where: { slug: { equals: slug } },
      limit: 1,
    })
    return docs[0] ?? null
  },
  ['page-by-slug'],
  { tags: [cacheTag('pages')] },
)

export default async function Page(props: { params: Promise<{ slug: string }> }) {
  await connection()
  const { slug } = await props.params
  const page = await getPage(slug)
  if (!page) notFound()
  // …
}
```

If a page shows data from several collections (a page plus its media), tag it
with each: `tags: [cacheTag('pages'), cacheTag('media')]`.

`'use cache'` / Cache Components aren't enabled: they prerender at build time,
which conflicts with the no-database build. Don't turn on `cacheComponents`
without solving that first.

### Add an environment variable

- **Server-only**: add it to `src/env.ts` (`required` or `optional`), then to
  `.env.example`, to the `x-app-env` block in `docker-compose.prod.yml`, and to
  `env:` in `.github/workflows/ci.yml` if tests need it. Read it as
  `env.NAME`, never `process.env.NAME`.
- **`NEXT_PUBLIC_*`**: inlined into the client bundle at build time. Read it as
  a literal `process.env.NEXT_PUBLIC_X`, add it as a build `ARG`/`ENV` in the
  Dockerfile and under `build.args` in the prod compose. Changing it needs a
  rebuild.

### Images

`Media` generates width-only WebP sizes (`thumbnail` 400, `small` 768,
`medium` 1280, `large` 1920); nothing is cropped. Point `next/image` or a
`srcset` at the closest size's `url` rather than the original. Cropping,
focal points and art direction are per-project decisions. SVG uploads are
blocked on purpose (they can carry script); see the comment in `Media.ts`.

### Email

`payload.sendEmail({ to, subject, html })`. Locally every message lands in
Mailpit at `http://localhost:8025` (or `MAILPIT_UI_PORT`). In production it
needs `SMTP_*` and `EMAIL_FROM_ADDRESS`: without them the migrate job and every request fail with an error naming the missing variables.

### Analytics and the cookie banner

With `NEXT_PUBLIC_GA_ID` set, the layout renders the consent banner, a "cookie
settings" button in the footer, and GA, which loads only after consent. Without
it, none of them render. Keep the footer button wherever the footer goes: it's
the only way for visitors to withdraw consent, which GDPR requires. Set
`site.privacyPolicyPath` once the site has a policy page. Banner copy lives in
`components/consent/copy.ts` (es, en). Custom events: `trackEvent()` from
`components/analytics/GoogleAnalytics.tsx`. For any other tool that sets
cookies, gate it on `useConsent()` the same way.

### Security headers and CSP

Every response gets `X-Content-Type-Options`, `Referrer-Policy`,
`X-Frame-Options: SAMEORIGIN` and `Permissions-Policy` (`next.config.ts`).
Caddy adds HSTS in production.

The Content Security Policy is **off by default**, because it depends on every
third party the site loads. To enable it:

1. In `next.config.ts`, list each third party's origins in `cspSources`
   (commented GA4 entries are there as the example; YouTube, maps, fonts, chat
   widgets, etc. each need their own).
2. Set `cspMode = 'report-only'`, run the site, visit every kind of page, and
   watch the browser console for "Content-Security-Policy-Report-Only"
   violations. Add what's missing.
3. Switch to `cspMode = 'enforce'` and check again.

The CSP covers the frontend only, never `/admin` or `/api`.

### Backups

`src/lib/backup/` creates and restores a single `.tar` (manifest, `pg_dump`
custom-format database, upload files). Three entry points share it: the admin
download (`GET /api/backup`, admins only, `components/admin/BackupPanel.tsx`
on the dashboard) and the `pnpm backup:create` / `backup:restore` scripts in
`scripts/`. The README covers using them.

Rules when touching it:

- Client tools must match the server's Postgres major (`pgTools.ts`). Bump the
  `postgresql17-client` package in the Dockerfile together with the
  `postgres:17` images.
- Every upload collection stored on local disk is included automatically. A
  collection moved to S3/cloud storage (`disableLocalStorage`) drops out of the
  backup, so its files need their own backup.
- The database restore is one transaction (drop + replay). Keep it that way;
  never pipe a partial dump into psql.
- Backups store applied migration names; restore refuses a backup with
  migrations the code doesn't have and runs `payload migrate` after.
- Backups don't include secrets (`.env`). Restoring into a site with a
  different `PAYLOAD_SECRET` logs everyone out, nothing worse (passwords are
  hashed independently of the secret).

## Decisions not to undo

- **`push: false`** in the Postgres adapter, in every environment (see the
  parity rule above).
- **`output: 'standalone'`** in `next.config.ts`: the Dockerfile copies
  `.next/standalone`.
- **`public/` exists even when empty**: the Dockerfile copies it.
- **`name:` pinned in both compose files**: otherwise volume names depend on
  the directory, and cloning into a differently named folder looks like data
  loss. `new-next` replaces `PROJECT_NAME`.
- **`NEXT_PUBLIC_*` as Docker build args**: they're inlined at build time.
- **No database access during the build**: the builder has no database, and
  `SKIP_ENV_VALIDATION=1` there means config values are placeholders.
- **The `migrator` stage inherits from `builder`**: the Payload CLI needs the
  TypeScript sources and full `node_modules`, absent from the standalone output.
- **Postgres has no `ports:` in production**, and binds to `127.0.0.1` in dev.
- **`caddy_data` is a volume to keep**: certificates and the ACME account.
  Let's Encrypt allows five duplicate certificates a week.
- **`/api/health` is blocked in Caddy**: Docker calls it from inside the
  container; it isn't for the public.
- **Container logs are capped** (`x-logging` in the prod compose), or they fill
  the VPS disk.
- **GraphQL is disabled.** Re-enabling it means `graphQL.disable: false` and
  restoring the two routes from `create-payload-app`.
- **Tests use `<db>_test`, never the dev database** (`tests/setup/`), and a
  temp uploads folder via `MEDIA_DIR`. Database test files run one at a time.
- **Backup tools match the server's Postgres major** (see Backups).

## Next.js 16 specifics already hit in this codebase

- `error.tsx` / `global-error.tsx` receive `retry`, not `reset`.
- `revalidateTag(tag, profile)` takes two arguments; the one-argument form is
  deprecated. We use `{ expire: 0 }` so editors see changes immediately.
- `global-not-found.tsx` needs `experimental.globalNotFound`, because the app
  has two root layouts (frontend and admin).
- `'use cache'` requires `cacheComponents`, which is off (see caching).

## Testing

- `tests/setup/testDatabase.ts` derives the test database from `DATABASE_URL`
  (`myproject` → `myproject_test`), creates it, and runs migrations on it before
  any test. CI passes a URL that already ends in `_test`.
- Integration tests use the Local API directly. `*.int.spec.ts` runs in Node,
  `*.int.spec.tsx` in jsdom.
- e2e tests use relative paths (`page.goto('/admin')`); `baseURL` is
  `http://localhost:3100`. Locally they run against `pnpm dev`, in CI against a
  production build.
- Test behaviour a user or editor would notice, not implementation details.

## CI

`.github/workflows/ci.yml` runs on PRs and pushes to `main`: `pnpm check`, a
check that generated types and the import map are current, a check that no
schema change is missing its migration, and `pnpm test:int`. e2e runs only when
triggered by hand. Client repos are private on GitHub's Free plan, which shares
a monthly pool of Actions minutes across all of them, so keep the default run
lean. Dependabot opens grouped PRs monthly.

## Maintaining the template

Projects copy the template once (`new-next`) and don't inherit later changes.
Tag a semver release for changes new projects should get. When a change also
needs `new-next` (in `~/automation`) to do something different, update both.
